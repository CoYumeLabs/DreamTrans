# 2026-09-21 实时转写延迟优化

本报告记录推送前的本地验证结果；远端 CI 状态以 `fix/realtime-latency` 分支拉取请求对应提交的检查为准。生产未部署本补丁。工作树 `/tmp/dt-realtime-latency`，基于 `948c97d71b4724cd168b5ae4e72467e129ef472f`。原工作树 `/root/DreamTrans` 中的升级补丁保持原样。

## 结论与边界

用户要求保留准确率，先减少可避免的等待。本次移除音频转发路径上的余额展示等待，并修复浏览器忙碌后部分字幕仍等待过期定时器的问题。模型、音频编码、采样设置、40 ms 音频帧、正常 50 ms 部分字幕刷新间隔、`max_delay: 2.0`、说话人配置均保持原样。

本次没有向真实 Speechmatics 服务发送测试音频，没有运行生产变更，也没有得到真实端到端转写延迟的前后对照。不能据合成测试承诺将用户看到的待确定平均约 1.2 s 降到某个数值。

原“升级后十几秒卡顿”故障尚未确诊。用户重新切换原新版镜像后，27 次分层 HTTP 检查均为 200，应用直连和本机入口为毫秒级，公网约 47–78 ms，随后一次 31 s 的转写也未再出现原症状。此前蓝绿同时在线的本地测试未复现“抢流量”。恢复现象不能证明历史故障的原因或已被本补丁修复。

## 两处等待及修复

### 音频预付成功后仍同步查询、发送展示余额

`backend/internal/handlers/speechmatics_proxy.go` 原来在每个预付窗口的 `RecordUsageBatch` 成功后，同步执行 `GetUserBalance` 和余额 WebSocket 写入，然后才允许音频继续转发。余额展示失败不改变已完成的扣费，但读取或发送耗时会阻塞音频。

新增 `speechmatics_balance.go`：每条连接使用一个通知 worker 和容量为 1 的唤醒通道，合并待通知的已提交成本。必要的预付扣费仍同步成功后才转发音频；查询展示余额和推送移到 worker。查询有 5 s 超时，没有自动重试循环。

结束时先停止并等待 worker，再按实际已转发音频结算，防止旧 WebSocket 余额覆盖最终结算余额。查询失败或结束时仍有未尝试通知的成本，则发送不带余额快照的成本增量。写入失败可能已送达，因此不重发同一成本。持久化账本仍是权威来源。已经进入 socket 写入时，停止仍需等待有超时限制的写入结束；本次没有消除慢客户端对下行发送的影响。

回归测试使用真实本地 WebSocket 和模拟上游：让余额查询持续阻塞，确认识别配置和跨两个预付窗口的六秒 PCM 字节仍原样转发。同时覆盖扣费失败拒发、通知合并不丢成本、取消查询、等待旧 writer、查询失败成本通知和写入失败不重复发送。

合成 benchmark 注入每次 20 ms 的余额查询，比较原实现与本补丁的同步预付入口：

| 实现 | 每次同步入口耗时 | 同步余额读取 |
| --- | --- | --- |
| 原实现 | 20.28–20.58 ms | 1 次 |
| 修改后 | 1.82–3.34 μs | 0 次 |

这里扣费使用测试桩，新入口 benchmark 不启动通知 worker，以单独测量移走的展示等待；真实 worker 行为由 WebSocket 回归测试覆盖。不能将此结果解读为生产数据库扣费只需几微秒，或转写整体提速若干倍。

### 部分字幕等待已经过期的定时器

`frontend/src/core/transcription/SpeechmaticsProxyClient.ts` 原先要求既没有排队的定时器、又达到 50 ms 间隔才立即应用新字幕。浏览器主线程忙碌时，旧定时器虽然已到期却尚未执行；新消息先到达处理函数仍会等待它。

修改为只要刷新间隔已满足，就取消旧定时器、清除其待处理内容并立即应用最新字幕。正常频率控制和最终稿优先级保留。确定性测试控制时钟和回调顺序，覆盖合并、过期回调、取消后不得恢复旧字幕、最终稿和空字幕清除；同一回归测试在原实现上失败。

### 异步余额显示的顺序保护

独立复核发现成本通知触发的 HTTP 余额刷新可能在最终 WebSocket 余额之后返回，造成展示回退。`useUnifiedAuth.ts` 现分别管理余额快照版本和账户详情请求版本，拒绝旧余额响应或错误清空新余额，同时保留在途账户详情；退出或切换账户时使两类请求同时失效。10 个新增浏览器回归覆盖真实录音 WebSocket → 余额推送 → 延迟 HTTP 的成功、失败、错误 owner，以及账户详情并发与身份切换。原实现已实测出现 US$7.25 被旧 HTTP 的 US$9.00 覆盖。

## 计费与强制停流专项

用户追加要求：优化不能引入绕过计费或无法切断流的问题。

预付门槛保留：开始识别前及滚动额度不足时，必须先成功提交下一窗口的扣费；余额展示 worker 不签发额度、不确认扣费，也不能改变预付失败的结果。新增真实本地 WebSocket 测试在首个 5 s 用完、余额查询仍阻塞时，分别让第二次预付余额不足、数据库失败和实际 context 超时。客户端额外排队 8 帧音频，供应商在三种情况下都只收到已付费的 160000 字节，没有第六秒或额外帧，只有两次预付尝试；失败预留按零实际用量进行独立于客户端 context 的结算。

专项审查还发现原有强制停流顺序先发客户端通知、再取消转写；新增异步余额 writer 可能与上行并行，使慢客户端写入推迟取消。因此本次同步加固：

- 管理员/会话管理终止先登记终止原因，取消 context 并直接关闭识别服务连接，不获取客户端或上游 writer 的互斥锁；错误退出也先关闭上游，再尽力发送浏览器通知。慢客户端可以延迟通知和清理，但不能因此维持上游音频转发。
- 心跳续期和取消时的读 deadline 共用独立小锁；取消后迟到的 pong 返回取消错误，不能重新延长读超时。该锁内不执行数据库查询或 socket 写入。
- 上行在读到帧后、预付成功后再次检查取消，避免取消时已经提交的新预留继续被使用；未转发部分仍走最终结算。测试覆盖扣费成功与取消相遇时不发送 `StartRecognition`，并将未使用额度按零用量结算。
- 转发 `EndOfStream` 后拒绝后续应用帧，同时保留客户端读取以检测断线。正常情况下下行继续接收最终稿和 `EndOfTranscript`，没有把发送结束误当作识别完成。
- 真正关闭连接可与 Gorilla WebSocket 读写并发；没有放开普通并发写限制。正常蓝绿 drain/handoff 的协作退出流程不变。

测试还覆盖 writer 锁占用时上游实际关闭（读超时不能算关闭）、客户端读循环被唤醒、EOS 后最终稿完整到达、客户端断线被检测、额外音频被拒绝。以上为实际 WebSocket、代理循环及终止 helper 的本地回归，未连接真实供应商；不能据此声称已经穷尽所有协议攻击面。

## 网络与当前指标

用户确认 200 ms 和 150 ms 是 ping 值。ping 已是 RTT；若分别代表浏览器到应用、应用到识别服务，两段上传加结果返回的网络部分可粗估为 200 + 150 = 350 ms，不能再乘二得出 700 ms。ICMP 路径、端点和负载可能与 WebSocket 不同，因此不是实测语音网络耗时或严格下限。流式音频持续发送，不会每 40 ms 音频帧都等待一个 RTT。

用户提供的“待确定最近 1.1 s、均 1.2 s；已确认最近 2.5 s、均 2.9 s；发送积压 0”是音频时间线到结果显示的指标，不能仅凭它定位网络或模型。发送积压为零仅覆盖浏览器发送队列，不等价于服务端或供应商没有积压。

Speechmatics 官方说明，部分结果的延迟不受 `max_delay` 控制；缩短最终稿等待或强制 `fixed` 可能影响准确率/实体格式。因此本次不调整这些参数。[官方延迟与准确率说明](https://docs.speechmatics.com/speech-to-text/realtime/output)

## 另外复现、未包含在本补丁的问题

计费的 `RecordUsageBatch` 已取得写事务连接后，定价读取又从同一连接池申请另一条连接。隔离数据库中将池限制为 1，单次操作等待约 1201 ms 后超时，连接池等待统计和 Go 栈确认在申请第二条连接；将池改为 2，同一操作约 28.6 ms 成功，重试未重复扣费。生产默认池大小为 25，这个实验没有证明生产当时耗尽连接，更不是原故障根因证据。

该问题还涉及 Edge 授权/续租及定价快照一致性，不能简单删除事务、改变隔离级别或放宽扣费门槛。诊断源代码、完整结果及修复设计边界单独保存在 `/tmp/dt-billing-pool-audit-evidence/`，本次未改动计费事务模型。因此本补丁不会消除必要扣费本身因数据库拥塞而产生的等待。
