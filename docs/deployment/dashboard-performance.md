# 后台概览性能排查与优化

## 2026-09-20 生产采样

后台默认概览调用 `/api/admin/dashboard`。管理员具备财务和指标权限时，接口串行执行 13 组统计，另读取供应商额度；健康检查接口的耗时不能代表此接口。

用户提供的只读查询采样中，13 组查询执行时间合计约 3.46 秒，另有约 49 毫秒规划时间。主要耗时为费用统计 1698.1 毫秒、时长分布 760.6 毫秒、编辑统计 453.2 毫秒。部分查询产生临时文件；主机采样时 CPU、可用内存及本机健康检查正常，不能据此排除其他时段的资源或 Cloudflare/浏览器问题。

同一诊断中，仅在诊断连接内关闭 JIT 后，费用统计为 545.5 毫秒、时长分布为 207.6 毫秒。这是顺序采样，缓存热度也可能影响差异，不能把全部差值归因于 JIT，更不能当成升级后的端到端耗时。

## 应用修复

- 仅后台概览的只读请求事务设置 `SET LOCAL jit=off`。提交、回滚、查询失败后不会将设置留在连接池，不改变 PostgreSQL 全局参数或实时计费连接。
- 费用统计每个时间段只汇总一次退款分摊，再计算消费额和利润；保留原先的退款前缀匹配、用户归属、零分母处理和 NUMERIC 精度。
- 时长分布先按用户、周聚合，再连接用户/周网格；仍保留零用量周、创建日期约束和日期范围边界。
- 查询失败日志带统计区块名，方便定位后续问题；不添加查询参数、账号内容或凭证日志。

无需数据库迁移或新增索引。退款、账本、用量写入及数据卷不变；兼容的蓝绿旧版本可按既有控制器流程回切。

## 验证范围

`console_dashboard_performance_test.go` 在隔离 PostgreSQL 中对照旧查询，以数据库 JSONB 数值比较验证日/周/月、UTC/纽约时区、渠道交集和空结果、重叠退款前缀、跨用户退款及零分母。另验证同一连接提交、回滚和查询失败后 JIT 设置恢复，并检查空白周及小时桶边界。

本地 PostgreSQL 16 隔离库模拟 12 用户、112157 条用量、12 条退款，容器上限 2 CPU / 1536 MiB。第二轮查询执行时间：

| 查询 | 旧查询，JIT 开启 | 旧查询，JIT 关闭 | 新查询，JIT 关闭 |
| --- | ---: | ---: | ---: |
| 时长分布 | 520.1 ms | 160.9 ms | 116.5 ms |
| 费用统计 | 1068.1 ms | 1002.4 ms | 452.2 ms |

这是合成数据的单机顺序基准，没有模拟所有生产数据分布、并发、网络或浏览器渲染，不作为生产延迟承诺。

## 发布后验收

使用经过 CI 验证的固定镜像，通过 `/root/dreamtrans/release.py ... deploy --image ...@sha256:...` 发布，随后查询状态。无需停止数据库或切换正式卷，不应通过全局关闭 JIT、增加全局 `work_mem` 或恢复旧数据库来替代本次应用发布。

使用相同管理员、相同筛选条件，在浏览器网络面板分别记录多次 `/api/admin/dashboard` 的响应时间、状态码，以及页面显示完成时间。首次和后续请求分别记录；不要分享带令牌的请求头或完整 HAR。确认金额、权限范围及零用量周显示正确。若其他后台页面仍慢，需针对对应业务接口测量，不能用概览优化代表所有页面均已解决。
